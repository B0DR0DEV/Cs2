# Strike Zone — архитектура (фаза 0)

Документ фиксирует ключевые технические решения до начала разработки. Все игровые числа, упомянутые здесь, — стартовые значения; источник истины — конфиги (`Assets/Resources/Config/*.json` на клиенте и серверные конфиги бэкенда).

Статус: **утверждено заказчиком** — Unity 6 LTS, сначала Android, первый заход = фазы 0 + 1.

## 1. Выбор технологий

### 1.1 Движок: Unity 6.3 LTS (6000.3.27f1), URP, C#

| Критерий | Unity 6.3 LTS | Godot 4 | Unreal 5 |
|---|---|---|---|
| Мобильная производительность (60 FPS на среднем Android) | хорошая, зрелый URP, ASTC, SRP Batcher, GPU Resident Drawer | средняя, мобильный рендер моложе | тяжёлый для среднего Android |
| Встроенные покупки | Unity IAP 5.x (Google Play Billing 7+, StoreKit 2) | плагины сообщества | плагины, сложнее |
| Сетевой код с предсказанием и лаг-компенсацией | несколько зрелых библиотек (раздел 1.2) | базовый уровень | сильный, но с упором на ПК |
| Headless Linux-сервер | Dedicated Server build target | есть | есть, тяжелее |
| CI сборка APK | game-ci (Docker-образы для каждой версии) | проще (без лицензии) | тяжелее |

Вывод: Unity — оптимальный баланс для мобильного соревновательного шутера. URP выбран вместо встроенного рендера ради SRP Batcher (меньше стоимость draw call), запекания света, отражений через Reflection Probes и масштабируемых пресетов качества.

Версия 6000.3.27f1 выбрана потому, что для неё есть Docker-образ `unityci/editor:ubuntu-6000.3.27f1-android-3`, на котором собирается APK в GitHub Actions.

### 1.2 Сетевой код: Fish-Net + собственная симуляция ядра

| | Netcode for GameObjects | Photon Fusion 2 | Fish-Net |
|---|---|---|---|
| Серверная авторитарность | да | да (Server Mode) | да |
| Предсказание и сверка (CSP) | нет из коробки | да, лучшее в классе | да (Prediction V2) |
| Лаг-компенсация хитбоксов | нет | да (Lag Compensated Hitboxes) | да (Colliders Rollback) |
| Тик-модель | есть | строгая тиковая | строгая тиковая |
| Стоимость | бесплатно | плата за CCU даже при своих серверах | бесплатно, исходники открыты |
| Контроль над деталями (субтик) | полный, но всё писать самим | ограничен API Fusion | полный |

**Решение: Fish-Net** как транспорт, репликация и тиковая инфраструктура; игровая симуляция (движение, оружие, урон) живёт в **нашем движконезависимом ядре** `StrikeZone.Core` (уже написано в фазе 1). Обоснование:
- Fusion 2 технически сильнее «из коробки», но плата за CCU на соревновательном шутере с выделенными серверами — постоянная статья расходов, растущая вместе с аудиторией. Fish-Net бесплатен.
- Субтиковый ввод (точный момент выстрела между тиками) требует контроля над форматом ввода и порядком применения событий. В Fish-Net это делается нашим кодом; в Fusion — через обходные пути.
- Ядро не зависит от сетевой библиотеки: если Fish-Net упрётся в ограничения, меняется только слой синхронизации.

### 1.3 Бэкенд: Nakama (Go) + PostgreSQL + Redis, игровые серверы на Agones

| | Nakama (self-host) | PlayFab | Свой Go/Node |
|---|---|---|---|
| Аккаунты, друзья, группы, чат | есть | есть | писать с нуля |
| Матчмейкер | есть (настраиваемый, со свойствами и расширением допуска) | есть | писать с нуля |
| Проверка чеков Google / Apple | есть (ValidatePurchaseGoogle / Apple, подписки, refund-хуки) | есть | писать с нуля |
| Транзакции в SQL для кейсов и рынка | да — свой Go-модуль работает напрямую с PostgreSQL | нет прямого SQL, только CloudScript | да |
| Привязка к вендору | нет, Apache 2.0 | высокая (Microsoft) | нет |

**Решение: Nakama** с серверными модулями на Go. Деньги, инвентарь, кейсы и рынок — собственные таблицы PostgreSQL в транзакциях `SERIALIZABLE` или с блокировками строк. Redis — кэш витрины, rate-limit, состояние очередей. Выделенные серверы — Unity Dedicated Server (Linux), оркестрация Agones на Kubernetes (аллокация сервера под матч, автоскейлинг по регионам). Nakama-матчмейкер → Agones Allocator → адрес сервера клиенту.

### 1.4 Конфиги

- Клиент/сервер матча: JSON в `Resources/Config` → загружаются в классы ядра (`WeaponDef`, `MovementConfig`, ...). В фазе 6 сервер матча получает конфиги из бэкенда при аллокации, клиент — сверяет хэш (несовпадение = обновление конфигов до входа в матч).
- Экономика, витрина, цены, шансы кейсов, региональные ограничения — только серверные конфиги в Nakama (storage + админ-панель), клиент их только отображает.

## 3. Сетевая модель

```
 Клиент (60–120 FPS рендер)                       Сервер матча (64 тика, headless)
 ┌──────────────────────────┐   ввод: тик + субтик  ┌──────────────────────────────┐
 │ Ввод → Core-предсказание │ ───────────────────▶ │ Очередь ввода по тикам       │
 │ локального игрока        │   (UDP, ненадёжный,  │ Core-симуляция всех игроков  │
 │                          │    с избыточностью   │ Лаг-компенсация: история     │
 │ Сверка: снапшот сервера  │    последних 3 тиков)│ хитбоксов 1 с (64 кадра)     │
 │ → откат и повтор ввода   │ ◀─────────────────── │ Выстрел: перемотка на        │
 │ Интерполяция остальных   │   снапшоты: дельты,  │ (тик выстрела − интерп.) +   │
 │ (буфер 2 тика ≈ 31 мс)   │   приоритет по       │ субтиковая доля              │
 └──────────────────────────┘   видимости          └──────────────────────────────┘
```

- **Тикрейт 64.** Ввод клиента — структура на каждый тик: оси движения, углы обзора, кнопки + список событий с субтиковой долей `0..1` (выстрел, прыжок, присед). Сервер применяет событие в точное время внутри тика: для выстрела — углы обзора интерполируются на долю тика, хитбоксы целей интерполируются между двумя сохранёнными кадрами истории.
- **Предсказание:** клиент гоняет то же ядро `PlayerMovement` для своего игрока; при расхождении позиции более 1 см откатывается к серверному состоянию и переигрывает неподтверждённый ввод.
- **Лаг-компенсация:** кольцевой буфер позиций хитбоксов 64 кадра; перемотка ограничена 200 мс (защита от «стрельбы из прошлого» при высоком пинге).
- **Разброс пуль детерминирован:** сид разброса = хэш(id игрока, тик, номер выстрела). Клиент рисует трассер туда же, куда сервер считает попадание; попадание решает только сервер.
- **Античит на сервере:** скорость ≤ лимит конфига + допуск, темп стрельбы ≤ `cycleTime`, проверка линии видимости при выстреле, проверка углов (нет мгновенных разворотов за 1 тик сверх предела), неожиданно точная статистика → метка для ручной проверки. Клиент не управляет здоровьем, деньгами, инвентарём, валютой.
- **Видимость (anti-wallhack):** сервер не отправляет позиции врагов, которых игрок не может увидеть или услышать (PVS по предрасчитанной сетке видимости карты + звуковой радиус).
- **Реконнект:** токен матча в бэкенде; при входе в приложение во время матча — кнопка «Вернуться в матч». Пока игрок вне матча, его контролирует бот; за выход — штраф (кулдаун очереди с нарастанием).

## 4. Бэкенд и модель данных

### 4.1 Сервисы
- **Nakama:** аутентификация (устройство → привязка Google / Apple / e-mail), друзья, статусы, группы (пати), чат, матчмейкер, RPC-модули Go.
- **Go-модули (наш код):** кошелёк, магазин, кейсы, рынок, контракт обмена, боевой пропуск, рейтинг Glicko-2, региональная политика, проверка чеков, обработка возвратов.
- **PostgreSQL:** всё, что связано с деньгами и предметами. **Redis:** витрина, кэш конфигов, rate-limit.
- **Обработка возвратов:** Google Real-Time Developer Notifications (Pub/Sub) + Voided Purchases API; Apple App Store Server Notifications V2 (`REFUND`, `REVOKE`).

### 4.3 Правила денег и предметов
- Все операции — одна транзакция БД: списание + выдача + запись в журнал. Идемпотентность по `request_id` клиента (повторный запрос не спишет дважды).
- Начисление Кредитов только после серверной проверки чека у Google / Apple и подтверждения покупки (acknowledge/consume) уже после записи в БД.
- **Возврат:** списываем Кредиты; если баланса не хватает — баланс уходит в минус (покупки блокируются до погашения), а купленные на эти Кредиты предметы, ещё не ушедшие на рынок, блокируются. Предметы, полученные из «отозванных» Кредитов, нельзя выставить на рынок 7 дней (`trade_hold_until`).

## 5. Магазин, кейсы, рынок — решения

### 5.1 Кейс без ключа
**Решение:** кейс открывается одной покупкой, цена указана на кнопке, отдельных ключей нет.
- Пара «кейс + ключ» скрывает реальную цену открытия и создаёт давление (кейсы падают бесплатно, «осталось только купить ключ»). Регуляторы и сторы относятся к таким схемам всё строже.
- Одна цена = прозрачная итоговая стоимость перед покупкой (требование ТЗ).
- Бесплатные кейсы за игру всё же выпадают, но открываются за **Монеты** (заработанную валюту), а не за деньги.

### 5.2 Шансы (серверный конфиг, отображаются в окне кейса до покупки)

| Редкость (рабочие названия) | Шанс |
|---|---|
| Стандарт | 79,92 % |
| Особый | 15,98 % |
| Элитный | 3,20 % |
| Легенда | 0,64 % |
| Реликвия (ножи и перчатки) | 0,26 % |

ГСЧ: `crypto/rand` на сервере. Для аудита сохраняются сид и все промежуточные значения броска (редкость, предмет, износ, паттерн). Клиент получает уже готовый результат и только проигрывает анимацию.

### 5.3 Износ
Float 0–1 → «Заводской» [0; 0,07), «Почти новый» [0,07; 0,15), «Полевой» [0,15; 0,38), «Потёртый» [0,38; 0,45), «Изношенный» [0,45; 1]. Сид паттерна 0–999 задаёт смещение и поворот процедурной маски.

### 5.4 Рынок — только за Монеты
**Решение:** торговля между игроками только за Монеты (их нельзя купить напрямую).
- Если бы рынок работал за Кредиты, предметы из кейсов получили бы цену, выраженную в купленной за деньги валюте. Тогда выигрыш в кейсе — это «приз, имеющий денежную стоимость». Это ключевой признак азартной игры в законах многих стран (Нидерланды, Бельгия, Великобритания, Австралия).
- Комиссия рынка 10 % — сток Монет против инфляции.
- Новые предметы (из кейса, магазина или контракта) нельзя продать 7 дней — защита от мошенничества с возвратами платежей.

### 5.5 Ранг: один общий, плюс статистика по картам
Glicko-2, один рейтинг на сезон. Раздельные рейтинги по картам дробят выборку, а на мобильном старте аудитория меньше, чем у ПК-игр. Это удлиняет калибровку и ухудшает подбор. Статистика побед по картам отображается в профиле.

## 7. Модель стрельбы и движения (реализовано в фазе 1)

### Движение (Source-подобное, `Core/Movement/PlayerMovement.cs`)
- Трение: `speed -= max(speed, stopSpeed) × friction × dt` (friction 5,2; stopSpeed 80).
- Ускорение: `addSpeed = min(wishSpeed − v·wishDir, accel × maxSpeed × dt)` (accel 5,5). Контр-стрейф получается сам: противоположное направление складывает трение и ускорение навстречу движению, поэтому остановка с 250 ед/с занимает около 80 мс.
- Максимальная скорость берётся из оружия в руках; ходьба — 52 %, присед — 34 %, в прицеле снайперки — скорость прицела.
- Воздух: ускорение 12 с ограничением wishSpeed 30 (воздушный стрейф как в Source), гравитация 800, прыжок 268 ед/с (≈ 55 ед высоты).
- Тегинг: попадание → множитель скорости 0,5…1, восстановление за 0,4 с.
- Урон от падения: начиная со скорости падения 580 ед/с, линейно до смертельной 1024 ед/с.
- Единицы: 1 игровая единица = 1/39,37 м (как дюйм). Слой Unity переводит в метры.

### Оружие (`Core/Weapons`)
- Неточность = базовая (стоя / присед) + движение (линейно от 34 % макс. скорости до максимума) + воздух + накопленная от выстрелов. Накопленная неточность экспоненциально спадает с периодом `recoveryTime` (отдельно стоя и в приседе).
- Отдача: фиксированный паттерн на каждое автоматическое оружие (массив смещений pitch/yaw по номеру выстрела), сбрасывается при паузе дольше `recoilResetTime`. Камера получает 50 % смещения (как aim punch), направление пули — 100 %.
- Разброс: детерминированный ГСЧ, равномерно по углу, радиус `r = inaccuracy × sqrt(rand)`.

### Урон (`Core/Combat/DamageModel.cs`)
- `урон = базовый × rangeModifier^(дистанция/500) × множитель зоны` (голова 4, грудь и руки 1, живот 1,25, ноги 0,75).
- Броня (кроме ног; голова — только со шлемом): в здоровье уходит `урон × armorRatio × 0,5`, в броню — половина остатка; если брони не хватает — излишек идёт в здоровье.
- Пробитие: у материала есть сопротивление на единицу толщины; у оружия — запас пробития. Урон после стены умножается на долю оставшегося запаса и на `0,85` за каждую пройденную поверхность. Пуля проходит не более 4 поверхностей.
